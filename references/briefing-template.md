# 情报报告骨架 + 对话内输出格式

> **对话内默认给结论 + 关键发现；存档时落 markdown 报告。**
> 深入模式会额外用 `scripts/render_briefing.py` 从 md 生成 **HTML + PDF**
> （机械生成，样式在 `assets/template/briefing.css`；**不要手写 HTML**）。
> 简要模式只给对话内结论 + md；**默认不生成 HTML/PDF**，用户点名要时才渲染。

---

## 一、默认形态：对话内输出

**结构（顺序不可乱，与新报告的章节顺序一致）**：

```
1. 【一句话结论】      直接回答用户的核心问题
2. 【关键发现】        3–7 条，按主题聚类；每条配 BV + 时间戳 + 交叉验证状态
3. 【冲突 / 未收敛】   两边都列，不下结论
4. 【缺口与建议】      B站上没覆盖的 + 下一步该去哪补
5. 【范围与偏差声明】  搜了几组词、命中多少、入选多少、算法排序不是随机抽样
6. 【信源地图】        N 条候选 × 双轴评级 × 冗余度 × 一句话定性（含直链）
```

> **信源地图在对话里放在最后**，与报告一致：它是**核对的入口**，不是阅读的入口。
> 但**不能省**——「全部候选都要出现」是这条流程的产物的一部分。

### 交付分层（批次 D7 · 默认先给决策层）

**默认层（决策层）≤ 25 行**——给「现在就要判断」的时刻：

```
1. 【一句话结论】      2–3 行
2. 【关键发现】        3–5 条，每条一行，带 BV 编号
3. 【主要冲突】        1–2 条，两边各一句
4. 【最大缺口】        1 条 + 建议去哪补
5. 【要不要继续】       一句话 + 「完整版见下」
```

**证据层（完整结构）**——默认层之后展开，给「要拿去用」的时刻。

**为什么分两层而不是压缩**：57 KB 报告不是给人一口气读完的，但**删掉它证据链就断了**。
压缩会丢证据，分层只是把「阅读顺序」工具化。
⚠️ 分层**不等于**给普通用户看简版——本 skill 的用户是来把议题理解透的，
决策层只是入口，证据层才是交付物本体。

**篇幅控制**：
- 结论 3 行以内
- 信源地图：**全部候选都要出现**
- 发现：只写有信息量的，**不写"某视频介绍了 X 工具"这种空话**
- 冲突：**这一节最有价值，不要为了"看着简洁"而删**

## 二、markdown 报告模板

### 2.0 章节顺序（2026-10-22 定稿，改之前先读完这段）

```
一、结论
二、发现            ← 态度类议题的「阵营表」是本节最后一个子节（2.x）
三、冲突与未收敛处
四、缺口与建议      ← 三类缺口 + 「下一步建议」
五、检索范围与偏差声明  ← 含「单轮开销」
六、信源地图        ← 当附录用：深挖对象 / 入选未深挖 / 淘汰清单（= 可追溯清单）
```

**为什么信源地图在最后**：初版把它放在 §二，读者读完第一屏就撞上一张
140 行的候选表，真正要看的判断被推到第三屏之后。信源地图的价值是**核对**
（"这条结论是哪条视频说的"），核对发生在读完判断之后，不是之前。
**它同时是「可追溯清单」**——每行都带 BV 直链，所以不再单列一节。

**为什么阵营表进「发现」**：阵营表不是信源清单，它是对发现的**归并**
（"这些说法能收敛成几种立场、各占什么位置"）。它排在发现之后、冲突之前。

### 2.1 渲染约定（决定 HTML 长什么样）

`scripts/render_briefing.py` 靠**约定的纯文本**上样式，不猜语义。写 md 时守住四条：

| 写法 | 渲染成 | 不写会怎样 |
|---|---|---|
| 评级写成**独立单元格**的 `A2` / `B2` / `C3`（字母 A–F + 数字 1–4） | 灰度徽章 + 悬停说明 + 顶部「信源评级分布」条形 | 没有徽章，概览条缺一半 |
| 交叉验证用 `✅`（多源独立）/ `◐`（部分印证）/ `⚠️`（单一来源） | 三档徽章 + 顶部「证据强度分布」 | 概览条缺一半，证据强度肉眼不可辨 |
| 缺口表里写 `结构性边界` / `检索未覆盖` / `本次未做` | 三种边框的徽章（实线 / 描边 / 虚线） | 三类缺口在视觉上无差别，读者会混 |
| 日期写 `2026-10`、时长写 `12:05` | 整格不换行 | 会在连字符处被拆成两行 |

> ✅ **评级口径不用你写**。HTML 里的「读图口径」块（A–F 与 1–4 各是什么意思）
> 由脚本生成——写进 md 只会让每篇都重复 200 字，而且各篇迟早不一致。
> 你唯一要保证的是：评级出现在**独立单元格**里，且含义与 `source-grading.md` 一致。

交付前跑一次：

```
python scripts/render_briefing.py --md "<报告>.md" --check
```

**三类缺口要分开写**——它们的含义和后续动作完全不同：

| 方向 | 类型 | 为什么 B 站上找不到 | 建议的替代渠道 |

## 五、检索范围与偏差声明

> 这一节**不该手写**。阶段 0 用 `registry_upsert(kind="protocol", ...)` 落盘协议，
> 本节从 `registry_get(kind="protocol", topic="<议题名>")` 的 `content` 取素材。

```
关键词组（N 组）：
  组 1 …（命中 x 条，新条目 y）
  组 2 …
去重后候选：M 条
L1 初筛（元数据 + 前 15 条评论）：剩 X 条
L2 严格筛（字幕侧 + 评论区侧双路）：剩 Y 条
最终纳入：Y 条

⚠️ 排序来自B站算法，非随机抽样：
   · 高播放内容被系统性高估（播放量与可信度无关）
   · 冷门但硬核的内容系统性低估
   · 算法偏好新内容，早期但更准确的条目可能未入围
本次未覆盖的可能方向：……
```

**上下文隔离**：本轮 N 条深挖（评论/字幕/弹幕）由子代理读取，主上下文只收
≤700 token 的结构化摘要；引用单条评论 ≤40 字并带赞数/楼层。
（没有子代理时改写为：本轮**未做上下文隔离**，深挖条数由 6–8 条降到 3–4 条，
评论原文已进主上下文——这是偏差，不是优点。）

**单轮开销**：这一行取自 `registry_upsert(kind="commit")` 返回的
`final_cost.md_line`，**原样粘贴，不要手算，也不要用 commit 之前查到的值**
（commit 之前查到的是快照，之后的收尾调用会让它偏低——2026-10-22 实测差 6.8%）。
返回里 `closed=false` 或带「⚠️ 本轮未收尾」字样时，说明窗口还没闭合，先 commit。样例：

**单轮开销**：上游调用 84 次｜评论行 1,240｜转写字符合计 21,300｜输出估算约 96,000 token（口径 CJK×0.7+其它×0.25，仅用于横向比较，不是账单）

### 阵营表的三条纪律

1. **一个阵营必须能用自己的话自洽**，不能用对手的框架转述（那是稻草人）
2. **"占据什么"要用可核对的量**（播放/赞/赞播比/评论数），不要写"很多人"
3. **阵营数一般 2–4 个**。超过 4 个说明还没抽象出结构，回去合并

> **为什么"占据什么"这一列最重要**：同一议题里，不同阵营占据的是
> **不同的注意力货币**——方案派占播放量、劝退派占高赞评论、娱乐派占点赞率。
> 三者互不相加，也不互相反驳。只写"有几种观点"等于没写。

### 观点分布 → 阵营/簇的映射（2026-10-21 实跑后定稿）

> 阶段 2 产出的观点分布是**「每条视频的评论区簇」**（4–8 个簇，三轴指标），
> 而阵营表是**「跨视频的阵营」**（2–4 个）。**两者之间缺一层映射。**

**Q1：一个评论簇要不要单独成为一行？**
**看议题类型，不看簇本身。**

| 议题类型 | 簇怎么处理 | 理由 |
|---|---|---|
| **态度类** | 簇**不单独成行**，先归并成 2–4 个**跨视频阵营** | 同一视频的 5 个簇常属同一阵营；按簇列会碎片化 |
| **方法类** | 簇**不单独成行，也不归并成阵营**——只作「发现」「冲突」两节的**取材来源** | 方法类没有"谁占什么注意力货币"的问题 |

**归并依据（态度类）**：看簇的**核心主张**是否自洽于同一个框架。
判据是**主张本身**，不是三轴数值——三轴只描述"这个簇多响"，不描述"它是什么"。

**Q2：「占据什么位置」用哪一层的量？**
**两层并列，不嵌套。** 阵营表用**视频级**指标（播放/赞/赞播比/评论数）；
簇级三轴**不折算进阵营**——折算会把两个不可通约的量强行相加（伪精度）。

**Q3：「冲突」这一节吃的是簇还是阵营？**
**冲突的最小单位是簇，但写进报告的是议题级的冲突行。**
被围攻型 / 主战场型的簇 → **各写一条议题级冲突行**（双方都列，不下结论）。

#### 两条通用纪律

1. **热度不排序，密度排序。** 不要按三轴数值从高到低排簇。
   已在**两个议题类型上各独立复现一次**（见 `references/opinion-distribution.md` §五）。
2. **簇不是发现。** 簇里出现的**具体事实**（数字、测算、从业者证词）才进「发现」表，
   标注**来自评论**（不是视频），并注明该条评论的赞与楼层。

#### 实测留档：方法类议题的簇 → 取材取舍（2026-10-21）

样本：BV1d8pU6xEZX 前 100 条顶层评论（`judge_depth=100`，议题 =「AI 自主浏览 B 站」）。

| 簇 | 赞占比（估） | 取材决定 |
|---|---|---|
| 玩梗 / 到报 / 身份扮演 | 约 63% | **不做证据**（情绪样本） |
| 污染批评 / 反对 | 约 19% | **做冲突行** |
| 成本吐槽 | 约 8% | 做发现 |
| 插件机制讨论 | 约 6% | 做发现 |
| **真实踩坑报告** | **约 4%** | **做发现**——赞数最低，信息量最高 |

**结论**：方法类议题里，最有方法论价值的簇是**全表赞数最低的一簇**。
⇒ 与「态度类里点赞率与信息量成反比」是**同一条规律**。

## 三、写作规则

### 证据强度三档（批次 D7 · 替代原来的 ✅/⚠️ 二分）

| 档 | 判据 | 写法 |
|---|---|---|
| **强** | ≥2 个**独立一手**来源互相印证（不同作者、不同材料） | ✅ 多源独立 |
| **中** | 1 个一手 + 1 个二手转述，或 2 个二手但口径一致 | ◐ 部分印证 |
| **弱** | 单一来源，或全部来自 AI 字幕转述 | ⚠️ 单一来源 |

**为什么必须三档**：原来的二分把「两个二手来源互相抄」和「两个一手来源独立一致」
都标成 ✅ —— 而这两者的可信度差一个量级。

### 三条硬规则

1. **每个进入「发现」的事实必须标来源**：BV 号 + 时间戳 + 评级。
2. **任何进入结论的事实必须有 ≥2 个独立来源，或追到一手**。达不到的，降级为「单一来源，未交叉验证」并明确标注。
3. **不许把「本次未覆盖」写成「没有」**。这两句话在读者眼里是完全不同的结论。

### 关于「结论」

- **给判断，不给综述**。用户要的是"所以呢"。
- 证据不足就**明说证据不足**，并说明缺什么。不要用"综合来看"糊过去。
- 结论里出现的每一个事实，必须能在「发现」里找到对应行。

### 关于「发现」

**不要复述视频内容。** 判据：

> 如果一行只是"某视频介绍了 X 工具"，删掉。
> 有用的形式是：「X 工具免费版每天 5 次调用（BVxxxx @03:12，B2，✅ 官网确认）」

### 关于「冲突」

**这一节的存在本身就是结论。** 它告诉用户：这个议题上还没有共识，或者存在基准差异。
**最常见的冲突来源是"基准不同"**——同一个数字，拿一线城市比和拿二三线城市比，结论相反。
遇到这种要**点出基准差异**，而不是宣布谁对谁错。

### 关于「缺口与建议」

三类缺口的判据（2026-10-21 三议题实证，2026-10-22 补第三类）：

| 类型 | 含义 | 下一步动作 | 替代渠道该写到多根本 |
|---|---|---|---|
| **检索未覆盖** | 这个方向**可能**在 B 站上存在，但这次没搜到 | **可再试**：换词族、补翻页、换限定词 | 具体到社区/站点 |
| **结构性边界** | 这类内容**在 B 站上根本不存在**（平台不是它的载体） | **换渠道**，别再搜 | 官方财报 / 社区 App 本身 / 线下 |
| **本次未做** | 材料和路径**都有**，只是预算/时间没用到 | **直接补做**，成本已知 | 写清"补哪一步"，如"回读 `grid[].file`" |

> ⚠️ **为什么要第三类**：旧三份报告里约一半「缺口」其实是"本次未做"，
> 却被写成和"结构性边界"同一种语气。后果是读者**把可补的东西当成不存在**。
>
> 💡 **「结构性边界」不是检索失败，是发现**：三个议题都撞上了
> 「各游戏的真实用户规模（DAU/MAU/流水）」在 B 站上只有二手转述——
> 因为 B 站**不是**承载这类数据的平台。写成"结构性边界 + 替代渠道是厂商投资者关系页"
> 才是准确表述。
>
> ⚠️ 判断方法：**如果你换了 3 组以上的词、翻完了页，仍然只能找到二手转述——
> 那就是结构性边界，不是你没搜好。**

## 五、输出前自检

```
python scripts/render_briefing.py --md "<报告>.md" --check
```

脚本会查（硬错 → 退出码 1）：

- [ ] 六节齐全且**顺序**正确（结论 → 发现 → 冲突 → 缺口 → 检索范围 → 信源地图）
- [ ] 「阵营表」在 §二 之内（态度类）
- [ ] 深入报告在 §五 写了「单轮开销」
- [ ] 标题后缀与所在目录的模式一致（`深入分析/` ↔ `…深入报告`）

脚本会给**提醒**（软错 → 退出码 0，但该改）：

- [ ] §五 有没有「上下文隔离」声明
- [ ] §六 有没有 `### 6.1`（深挖对象与未深挖候选必须分开）
- [ ] 同一议题的同一 BV，两份报告的信源地图评级字母是否一致
- [ ] 是否残留旧版编排痕迹（信源地图在 §二 / 独立的可追溯清单）

人工自检（脚本查不出来的）：

- [ ] 结论里的每个事实都能在「发现」里找到出处
- [ ] 所有候选都出现在信源地图里（包括被淘汰的）
- [ ] 冲突与未收敛处**非空**（真的没有冲突时，写明"本次未发现冲突"）
- [ ] 偏差声明齐全（关键词组、漏斗数字、算法偏差）
- [ ] 信源地图里没有「（见 6.1 #N）」这类指代行顶替真实条目
- [ ] 区分了「未覆盖」和「没有」
- [ ] 没有把单一来源写成已证实的结论
- [ ] 不含读者个人信息（可对外分享）
- [ ] **已更新 `sources.json` 与 `videos.json`**，且 `registry_upsert(kind="commit")` 已执行
