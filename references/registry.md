# 信源库与资产积累

> 用户拍板：**这是「资产积累型」skill，不是「用完即弃」型。**
> 所以三个持久化文件是**流程的一部分**，不是可选项。
> 这是本 skill 与精读 skill 在工程上最大的差别。

---

## 一、目录位置

**默认根目录** = 项目目录下的 `.registry/`（已被 `.gitignore` 排除）；
需要换位置时设环境变量 `BIG_REGISTRY_DIR`。

> 🔴 **2026-10-22 起，报告不再放在这里。** `.registry/` 只放**机器资产**
> （信源库 / 视频索引 / 议题档案 / 检索协议 / 观点簇 / 调用账本）。
> 给人读的 md / HTML / PDF 落在项目根目录的 **`分析报告库/`**（中文名，不隐藏）。
> 理由很实在：以点开头的目录在文件管理器里默认不显示，用户找不到自己刚生成的东西；
> 而且清理资产时容易连报告一起删。

```
<项目目录>\.registry\
├── sources.json      信源库：UP 主 / 系列
├── videos.json       已分析视频索引
├── topics.json       议题档案：每个议题的核心问题/覆盖/缺口/用户采纳（批次 B4）
├── staging\          写侧暂存区（批次 C1：commit 之前正式库不被改动）
│   ├── sources.json  暂存的信源记录
│   ├── videos.json   暂存的视频记录
│   ├── insights.json 暂存的经验条目
│   ├── topics.json   暂存的议题档案
│   └── protocols.json 暂存的检索协议
├── cost-log.jsonl    调用账本（一行一次工具调用；超 512 KB 按月归档，批次 F）
├── cost-log-<YYYYMM>.jsonl  归档（保留最近 12 个月）
├── topics\           议题**资产**目录（⚠️ 不含报告）
│   └── <议题>\
│       ├── protocol.md       阶段 0 的产物落盘（固定模板）
│       ├── protocol.sha256   版本账本
│       ├── protocol.md.new   你手改过时，新版另存这里
│       ├── run-<YYYYMMDD>.json  每次运行的漏斗数字（同日第二次运行另存 -2）
│       └── clusters.json     观点簇（归簇痕迹）
└── insights.md       经验沉淀
```

**报告在哪**（两处分工，别混）：

```
<项目目录>\分析报告库\
└── <YYYYMMDD>-<深入分析|简要分析>-<议题>\
    ├── <议题>·B站信息深入报告.md      ← 唯一真源（Agent 手写）
    ├── <议题>·B站信息深入报告.html    ← scripts/render_briefing.py 生成
    └── <议题>·B站信息深入报告.pdf
```

**为什么放在项目里而不是 skill 目录里**：
- skill 目录放**方法论与模板**（静态），registry 放**运行数据**（动态）——生命周期不同，
  升级 skill 不该动数据
- 放在项目内 = 换机器时 `git clone` 之外只需拷这一个目录
- 开源时它**不进仓库**：里面是使用者自己的评级与历史，与项目本身无关

> ⚠️ `.registry` 以点开头是**故意的**：不和 `.md` 报告混在一起，默认隐藏。

## 二、`sources.json` —— 信源库（最值钱的资产）

### 结构

```json
{
  "_meta": {
    "version": 1,
    "updated": "2026-10-16",
    "note": "UP 主/系列的信源评级库。评级含义见 skill 的 references/source-grading.md"
  },
  "sources": [
    {
      "mid": 1234567,
      "name": "某UP主",
      "domains": ["AI工具", "本地部署"],
      "grade": "B",
      "grade_basis": "横评 8 款工具，附价格表与实测截图；连续 3 期数据准确",
      "first_seen": "2026-10-16",
      "last_updated": "2026-10-16",
      "observations": 3,
      "conflicts": [
        {
          "date": "2026-10-16",
          "note": "在 XX 议题上与其历史评级不符：讲了不熟悉的领域，无实测依据"
        }
      ],
      "notes": "偏保守，不追热点；更新频率低但每期信息密度高"
    }
  ]
}
```

### 字段说明

| 字段 | 说明 |
|---|---|
| `mid` | B站数字 ID（**稳定标识**，比用户名可靠——用户名会改） |
| `domains` | **这个评级在哪些领域成立**。跨领域发言不自动继承评级 |
| `grade` | 来源轴 A–F（**只记来源轴，不记可用度**——可用度是相对单个议题的，不跨议题） |
| `grade_basis` | **评级的依据**。没有依据的评级等于没有评级 |
| `observations` | 累计观察次数。次数越多，评级越可信 |
| `conflicts` | **与历史评级不符的记录**。空白不代表没有，代表还没遇到 |
| `notes` | 行为特征（更新频率、风格、利益关系） |

### 使用规则

**读（每次任务开始时）**：
```
若候选的 UP 主已在库中，且议题领域 ∈ domains：
  → 沿用 grade，标注「沿用历史评级（<日期>），本次未复核」
  → 可用度仍需重新判断（那是相对本议题的）

若议题领域 ∉ domains：
  → 评级不可沿用，必须重新判断来源轴
  → 但可以把历史评级作为先验，写进判断依据
```

**写（每次任务结束时）**：
```
新 UP 主    → 入库
已有 UP 主  → observations +1；last_updated 更新
            若本次评级与历史不符 → 追加一条 conflicts 记录
```

> 💡 **`conflicts` 是最容易被忽略但最有价值的部分**。一个靠谱的 UP 突然发了条不靠谱的内容，或者反过来——**这种不一致本身就是信息**，说明"评级"不能机械套用。

## 三、`videos.json` —— 已分析视频索引

### 结构

```json
{
  "_meta": { "version": 1, "updated": "2026-10-16" },
  "videos": {
    "BV1xxxxxxxxx": {
      "title": "完整标题",
      "mid": 1234567,
      "analyzed_at": "2026-10-16",
      "topics": ["视频转笔记工具"],
      "grade": "B2",
      "redundancy": "原创",
      "key_findings": [
        "免费版每天 5 次调用",
        "导出格式支持 Markdown/PDF/Word"
      ],
      "transcript_pulled": true,
      "verdict": "本议题下最值得深挖的一条"
    }
  }
}
```

### 为什么要这个库

**跨任务去重。** 一个议题可能被研究两次（比如半年后想再看一眼）。有了这个库：

- 已分析过的视频 → **直接复用结论**，只补新出现的条目
- 用户问"我以前是不是看过这个" → 能查
- 判断"某个 UP 主在这个议题上的输出是不是系统性的" → 看他有几条进了库

### 字段说明

| 字段 | 说明 |
|---|---|
| `grade` | 本条视频的完整编码（来源 + 可用度）——**这是相对议题的，所以每条都要单独记** |
| `redundancy` | 原创源 / 冗余源 / 冲突源 |
| `key_findings` | **只记结论级的事实**，不记过程。控制在 5 条以内 |
| `transcript_pulled` | 是否拉过字幕（决定下次要不要重拉） |
| `selected_because` | **为什么这条被选进来**（命中哪个核心问题 / 哪个词族）。批次 B4 新增——它让"为什么这条被选进来"在半年后仍可查，避免同一个错误条目被反复选中 |
| `cross_checked_with` | 与哪几条交叉验证过（BV 号列表）。批次 B4 新增 |
| `degraded` | 本次这条的缺口（无字幕 / 只读了第 2 部分 / 判读深度不足…）。批次 B4 新增 |

## 四·A `topics.json` —— 议题档案（批次 B4）

**它是什么**：**单个议题**的结构化档案——跨任务记忆 + 反馈闭环的落点。

**和 `insights.md` 的分工**（别混用）：

| | `insights.md` | `topics.json` |
|---|---|---|
| 范围 | **跨议题**的通用认知 | **单个议题**的进展 |
| 形态 | 追加式 markdown（人可读、可手改） | 结构化 JSON（可查询） |
| 回答 | "下次能省什么" | "这个议题查到哪了" |

```json
{
  "topics": {
    "主流二游社区": {
      "topic": "主流二游社区",
      "core_questions": ["6 款二游各自社区形态与变化", "跨游戏社区的关联/对立", "热闹的受众广度机制 vs 争议度机制"],
      "searched_axes": ["原神 玩家 争议", "二游 玩家 社区", "终末地"],
      "covered": ["厂商—玩家信任层", "玩家—玩家强度层"],
      "gaps": ["终末地社区规模", "2026 年时间序列"],
      "open_conflicts": ["终末地开服是烂还是被造谣"],
      "user_adopted": ["异格银灰争议是社区节奏的典型样本"],
      "next_entry": "补 4 条高价值视频的字幕与评论",
      "updated": "2026-10-21"
    }
  }
}
```

**`user_adopted` 是这个结构的核心**：它记录**用户在本议题上采纳了哪些发现**
（等价于 DSH 插件的"你点了赞"）。有了它，"下次第几轮该往哪深挖"就有**外部信号**，
而不是 Agent 自己猜。

## 四·B 检索协议（批次 B2）

**它是什么**：**阶段 0 的产物落盘**——"这次搜了什么、为什么这么搜"永远可回放。

**为什么要它**：阶段 0 产出的五样东西（核心问题 / 关键词族 / 纳入排除 / 预算 / 已有资产）
以前**只存在于 Agent 当轮的上下文里**。后果：
* 报告 §五「检索范围与偏差声明」是**手写**的 → 写错无法发现
* 同一议题第二次跑，**不知道上次搜过什么词、覆盖了哪些方向** → 重复劳动 + 覆盖缺口不可见
* `videos.json` 只有 `topics` 标签，**不保存"为什么这条被选进来"**

**落盘结构**：

```
.registry/topics/<议题>\
├── protocol.md        固定模板：核心问题 / 关键词族及各自命中 / 纳入排除 / 预算 / 已知资产
├── protocol.sha256    版本账本（对齐 DSH 的 charter.sha256 范式）
├── protocol.md.new    你手改过时，新版另存这里
└── run-<YYYYMMDD>.json  每次运行的漏斗数字
```

**升级规矩**（同 DSH 插件的 `duty.md`）：
* **没改过**（哈希与账本一致）→ 自动升级，直接覆盖
* **改过**（哈希与账本不符）→ **保留你那份**，新版另存 `protocol.md.new`

为什么要有这个分支：协议是「用户可以手工调」的判据载体。
每次写入都直接覆盖的话，用户手写的排除条件会被悄悄冲掉——
而那正是"我上次调过，这次别再搜那些垃圾"的信息。

**报告 §五 从这里读出来**，不再手写。

## 四·C 写侧暂存区（批次 C1）

**规则**：`registry_upsert` 的所有写操作**默认只进暂存区**（`.registry/staging/`），
**正式库在 `kind="commit"` 之前不会被改动**。收尾时：

```
registry_upsert(kind="commit")    # 一次合并进正式库，并清空暂存区
registry_upsert(kind="discard")   # 丢弃（这轮白跑了）
registry_get(kind="staging")      # 看暂存区里有什么
```

**为什么**：DSH 插件的范式是「能力最小化」——一轮里只给模型几个只读工具，
写侧的工具**连名字都看不到**。本项目的等价实现是**延迟合并**：
写侧**始终可用**（不打断"边挖边记"），但**碰不到正式库**。

> ⚠️ 这意味着**收尾必须记得 commit**。忘了 commit ⇒ 本次成果留在暂存区，
> 下次任务读 `registry_get(kind="stats")` 看不到它们。
> 暂存区里的东西**不会**被自动合并。

**合并语义**：source 走正常 upsert（评级变动检测照旧生效）；
insight 追加进 `insights.md` 并**按正文去重**（同一条经验不会被写两遍）。

**video 是合并，不是覆盖**（2026-10-22 实测事故后改的）：同一议题先跑深入、
后跑简要，两次都会 commit。旧实现整体替换，于是"没读字幕"的那一轮
把深入轮的 `key_findings` 与 `grade` 一起冲掉，`transcript_pulled` 还从 `true` 变回 `false`。
现在的规则：

| 字段 | 合并方式 |
|---|---|
| `key_findings` | 并集，旧的在前（旧的通常更深），上限 12 条 |
| `transcript_pulled` | **只升不降**——读过就是读过 |
| `topics` | 并集 |
| `grade` | 旧记录读过本体、新记录没读、议题是子集 ⇒ **保留旧评级**，新评级进 `grade_history`（`kept:false`） |
| 其余 | 新值优先 |

commit 的返回里，被改动的视频带 `changes`（`grade` / `grade_kept` / `findings_kept` / `transcript_preserved`），
所以"这一轮把什么改了"在收尾时就能看见，不用等半年后发现数据少了。

## 四·D 调用账本（批次 D5 / 批次 F 加轮转与单轮窗口）

**它回答什么**：跑一轮议题到底花了多少。这是「深入分析值不值」唯一的量化依据，
也是报告 §五「单轮开销」那一行的数据源。

```
.registry/cost-log.jsonl              一行一次工具调用（追加写，失败静默）
.registry/cost-log-<YYYYMM>.jsonl     归档（超过 512 KB 触发，保留最近 12 份）
```

**每行的形状**：

```json
{"ts":"2026-10-22T11:50:03","tool":"scan_topic","calls":48,"comment_rows":180,
 "transcript_chars":0,"est_output_tokens":12000}
```

**单轮怎么切**——靠显式标记，不靠时间启发式：

```
registry_upsert(kind="run-start", topic="<议题名>")      # 阶段 0 收尾打一次
registry_upsert(kind="commit")                          # 收尾：自动打 run-end，返回 final_cost.md_line
registry_get(kind="cost", window="run")                 # 补查：只读，已闭合则数字不变
registry_get(kind="cost", window="runs")                # 每一轮各一行，用来对比深入 vs 简要
```

**为什么要有 run-end**：只有 run-start 时，窗口的右边界是"现在"。
Agent 在写完报告时取一次 `md_line` 贴进 §五，然后才 commit / 渲染——**这几步本身也记账**，
于是报告里的数字永远小于账本后来的读数。实测 88,515 vs 94,916（低 6.8%），
两次查询都"正常返回"，没人会发现。run-end 把窗口闭合后，这个数此后不再变。

**未闭合时必须自曝**：`md_line` 会带「⚠️ 本轮未收尾，数字可能偏低」，`closed` 为 false。

**为什么不用"两条记录间隔 < N 分钟算同一轮"**：ASR 一次就可能跑 10 分钟，
真实的一轮里天然存在长间隔。用时间切片会把一轮切成两轮，数字看着像半途而废。

**为什么必须轮转**：一行一次调用，单轮 30–90 行。长期用文件无限长，
每次汇总都要把整份文件读进内存。按月归档 + 只留最近 12 份，增长有上界。
归档是**追加**到同月文件的，不会因为一个月轮转两次而丢前半段。

**口径（引用时必须带上）**：

| 字段 | 是什么 | 能不能报账 |
|---|---|---|
| `calls` | 真的打了几次上游（`http.call_count` 差值） | ✅ 是事实 |
| `comment_rows` / `transcript_chars` | 实际读进来多少 | ✅ 是事实 |
| `est_output_tokens` | 输出侧粗估：CJK×0.7 + 其它×0.25 | ❌ 只用于横向比较 |

> ⚠️ `est_output_tokens` **不是账单金额**：真实费用要乘供应商单价，
> 且输入侧 token（模型读到的返回）没算进来。把它当报价是误用。

## 四、报告存档：`分析报告库/`（2026-10-22 从 `.registry/topics/` 迁出）

- 根目录：项目目录下 **`分析报告库/`**（中文名，用户自己找用；已在 `.gitignore` 里）
- 子目录：`<YYYYMMDD>-<深入分析|简要分析>-<议题>`
- 文件：`<议题>·B站信息深入报告.md`（简要模式为 `<议题>·B站信息简报.md`），HTML/PDF 同名
- 同一议题多次研究时**不覆盖**——日期在目录名里，两轮各一个目录（便于看结论怎么变）
- 格式见 `references/briefing-template.md`；**路径由 `python -m big.cli report-path` 算，不要手拼**

**检索方式**：文件少时按目录名找（日期在前、议题在后、模式在中间）；
多起来之后可以靠 `videos.json` 的 `topics` 字段反查，或 `registry_get(kind="stats")`
里的 `reports.recent`。

## 四·B `insights.md` —— 经验库（"越用越实用"真正发生的地方）

单议题简报是**结论**，经验库是**能力**。前者回答"这次查到了什么"，后者回答"下次能省什么"。

### 结构

```markdown
# 经验沉淀

## 2026-10-19 · 普通人如何投资

- **[领域]** B站财经区的收益预期普遍锚在 8–10%，任何"提前退休"测算先查这个锚是否被质疑过
- **[信源]** 某 UP 的数据均为二手转述，引用前必须找他引的原报告
- **[方法]** 热点词族（番剧名）会带入大量分集与二创，40 条候选里 12 条无效，阶段 0 要预判
```

### 三类，各有各的用途

| 类 | 回答什么 | 为什么会过期 |
|---|---|---|
| **[领域]** | 这个领域的事实性理解 | 市场/政策变了会过期 → 季度复核 |
| **[信源]** | 谁在什么问题上可信，**为什么** | UP 会转型 → 评级变动自动记 conflict |
| **[方法]** | 流程哪里失准 | 流程改了就作废 → 改流程时同步删旧条目 |

### 三条硬规则

1. **不写数据，写判断。**
   ❌「阿Test 那条 105 万播放」 ✅「财经区的收益预期锚在 8–10%，要用先查这个锚」
2. **不写本次结论，写可迁移的认知。**
   简报里已经有的东西不要再抄一遍——那是重复，不是沉淀。
3. **写完自检：这条会帮到下一个议题吗？** 不会就别写。经验库最怕的不是空，是垃圾。

### 维护：只增不压会烂掉

| 触发 | 动作 |
|---|---|
| 文件 > 64 KB | 同类合并：把同一领域的多条压成一条，删掉已被推翻的 |
| 某条判断被新证据推翻 | **直接删掉并在 CHANGELOG 记一句**，不要留着"以防万一" |
| 每季度 | 通读一遍，删过期项（`stats` 的 `insights_note` 会提醒体积） |

> 经验库的价值密度随时间**下降**——因为旧判断会混进新任务里误导人。
> 定期压缩不是洁癖，是防污染。

---

## 五、维护规则

| 时机 | 动作 |
|---|---|
| **任务开始前** | 读 `stats` + `insights`（全量），把相关条目摘出来写进「阶段 0 产出清单」 |
| **定级每条候选后** | 临时记在内存，**任务结束时统一写盘**（避免中途失败留半成品） |
| **任务结束后** | 更新 `sources.json` + `videos.json` + **`insights.md`（必写）**；落简报（如果要存档） |
| **季度（建议）** | 检查 `sources.json` 里 `last_updated` 超过 12 个月的条目，标记为「可能过期」；压缩 `insights.md` |

### 用工具做，不要手写 JSON

```bash
# 查一个 UP 主 / 视频 / 列表
python -m big.cli registry sources --domain "投资理财"
python -m big.cli registry videos --topic "普通人如何投资"
python -m big.cli registry stats
```

写入走 MCP（`registry_upsert`）或 Python 里的 `big.registry`：
`upsert_source(rec)` / `upsert_video(rec)` / `append_insights(topic, records)`。

手写 JSON 容易漏逗号、编码错、并发覆盖。**一律通过工具写。**
