# 阶段 0 · 检索协议

> **这一步最容易被跳过，但最决定成败。** 没有检索协议就直接搜，等于把方向交给算法排序。
> 依据：Rapid Evidence Assessment（REA）方法论——「检索式与纳入/排除标准必须先写死，不能一边筛一边改」。

---

## 一、第一件事：确认用户到底想问什么

**🔴 硬规则：如果用户的原始表述里没有说明"要用来做什么"，必须先反问一次，不能替用户假设。**

### 为什么要反问

同样一句「我想了解 XX 工具」，四种意图的检索策略完全不同：

| 用户真实意图 | 核心问题类型 | 检索重点 | 容易翻车的搜法 |
|---|---|---|---|
| **选型**（我要不要用） | 决策型 | 价格 + 免费额度 + 横评对比 | 只搜"XX 介绍" → 全是官方宣传 |
| **写东西引用**（我要写进文章） | 引用型 | 权威表述 + 可溯源数据 | 只搜热门视频 → 找不到可引用的原始数据 |
| **避坑**（我怕踩雷） | 风险型 | 负面评价 + 退款/封号/涨价 | 只搜好评 → 完全看不到风险 |
| **学习**（我要学会） | 教程型 | 操作步骤 + 前置要求 | 只搜概念介绍 → 拿不到可执行步骤 |

**问错方向，后面越努力越偏。**

### 反问的模板（简洁、带选项，不让用户费神）

```
在开始搜之前确认一个方向——你更关心哪一类：
  □ 有哪些选择、各自什么水平（枚举 + 评估）
  □ 该不该用某个具体的（决策）
  □ 有没有人踩过坑、有什么风险（风险）
  □ 具体怎么做（教程）
  □ 别的：______

另外：有没有你已经知道的、不需要我重复找的？
```

## 二、核心问题：把"想了解"变成"可回答"

**规则**：拆成 **1–3 个可验证的问题**。超过 3 个说明议题太宽，需要跟用户收窄。

**示例**——

用户说：「我去 b站了解一下视频转笔记的工具」

| 拆解 | 类型 | 决定了什么 |
|---|---|---|
| 市面上有哪些工具？ | 枚举型 | 检索面要**宽** |
| 它们各自的能力边界在哪？ | 评估型 | 重点找**横评 / 对比**类内容 |
| 免费版和付费版的真实差别？ | 决策型 | 找**价格页 + 试用反馈** |
| 有没有人踩过坑？ | 风险型 | 专门找**负面评价** |

> ⚠️ **这四个问题的检索策略不同，但可以用同一组关键词覆盖。**
> 区别在于**筛选时的权重**：评估型优先保留横评，风险型优先保留吐槽。

## 三、关键词族设计（决定样本量上限）

### 硬约束

> **本项目的搜索上限是 50 条/次**（`per_query` 的硬上限，`scan_topic` 与 `search_videos` 都一样）。
> 所以：**关键词组数 × per_query ≈ 你能覆盖的候选上限**（去重前）。
> 6–8 组 × 30 条 ≈ 180–240 条命中 → 去重后通常剩 100–150 条。

> ⚠️ 旧版这里写的是「一次最多返回 10 条」——那是**上游 bilibili-mcp 的 schema 限制**，
> **不适用于本项目**。照着它估样本量会把候选池低估 5 倍。

### 五类词，缺一不可

| 类别 | 作用 | 例（以"视频转笔记工具"为例） |
|---|---|---|
| **① 同义词** | 覆盖不同的说法 | 视频转笔记 / 视频总结 / AI 笔记 / 视频摘要 / 字幕转文字 |
| **② 上位词** | 找到宏观盘点类内容 | AI 效率工具 / 生产力工具 / 信息处理 / 学习工具 |
| **③ 下位词（具体产品名）** | 找到单点深度评测 | BibiGPT / 通义听悟 / 飞书妙记 / Napkin |
| **④ 黑话 / 口语** | 找到真实用户表达 | 一键总结 / 视频生笔记 / 看视频神器 / 懒得看 |
| **⑤ 英文对照** | 找到引进/翻译类内容 | video to notes / AI summarizer / transcript tool |

> 💡 **第 ④ 类最容易被忽略，但命中率往往最高。** 普通用户不会说"视频转笔记工具"，他会说"有没有什么神器能一键总结"。

### 🔴 同一族内的关键词，必须用**不同的主词**（2026-10-21 实测教训）

**这是"跨词命中数"这个排序信号能不能用的前提。**

实测（上一轮「AI Agent 自主学习与B站」议题）：6 组词里有 **3 组以同一主词 "deepseek" 为核心**
（`deepseek 刷b站` / `大肥鱼 deepseek 插件` / `DSH deepseek harness`）
⇒ Top 候选普遍命中 5–6 组 ⇒ **排序被冗余关键词放大**，"在议题中心"这个信号被高估。

**规则**：
* 一族里的关键词，**主词要不同**。要深挖同一主词，就**归成一族**（`scan_topic(families=...)`），
  而不是拆成三组"看起来不同"的词。
* 判断方法：**两组的词如果共用一个主词，它们不是两组，是一组。**

> ✅ 对照（二游议题的做法是对的）：6 组词里**只有 2 组**共用「二游」主词，其余各用各的主词
> （原神/鸣潮/崩铁/明日方舟/绝区零/终末地）——**刻意混主词**，避免跨词命中数失真。

### 🔴 词族探针：花 0–3 次调用验证假设，别直接广扫

**问题**：词族是**假设**，不是事实。你以为「原神 玩家」能搜到社区讨论，
它可能给你的是搞笑短视频和 AI 整活。
2026-10-21 二游议题实测：

```
探针 1  「原神 玩家」     → 20 条里约 15 条是 9–135 秒搞笑/抽象/二创，社区分析稀少
探针 2  「二游 玩家 社区」→ 命中全部三条核心视频（本次最有效的词族）
探针 3  「终末地」        → 20 条里 18 条是剧情解析/角色 PV/同人/攻略，社区讨论仅 1 条
⇒ 结论：裸游戏名 ≠ 社区讨论；带「社区/玩家/争议/节奏」限定词才有效。
```

**做法**（**广扫之前**）：
```
对最不确定的 1–2 个词族，各跑一次 search_videos(keyword=..., limit=20)，
看前 10 条是不是真的在讨论这个方向。
  · 是 → 保留该族
  · 不是 → 换限定词（加「社区/玩家/争议/节奏/黑话」）或整族换掉
```

**成本**：0–3 次调用，**相对一次 `scan_topic`（40 条候选）几乎可忽略**。
**收益**：避免用一个错词族跑完整轮才发现方向不对。

> 💡 **探针结果要写进 `protocol.md` 的「关键词族及各自命中」**——
> 它证明哪些族成立、哪些被换掉了，这是"可回放"的一部分。

### 关键词族的产出格式

```
组 1  视频转笔记工具
组 2  视频总结 AI 工具
组 3  AI 笔记 效率
组 4  一键总结 视频
组 5  BibiGPT 测评
组 6  通义听悟 对比
组 7  飞书妙记 体验
组 8  视频 转文字 工具
```

**搜索时的注意**：
- **每组单独搜**，不要试图用长句（B站搜索是关键词匹配，不是语义搜索）
- 组之间**主动制造差异**——如果两组搜出来的前 10 条高度重叠，说明这组词是冗余的，换掉
- 记录**每组命中的去重贡献**（哪组带来了新条目）→ 这是后续优化关键词族的依据
- **把族显式传给 `scan_topic(families={...})`**（批次 B3 新增）——
  排序键会变成「命中的**不同语义族数** → 族内命中数 → 播放量」，
  冗余主词不再放大排序信号。**不传的话 `kw_families` 会是 `null`**（算不出来就如实说）

## 四、纳入 / 排除标准（写死，中途不改）

### 默认标准（按议题可调，但必须在检索前定）

```
纳入：
  · 时长 ≥ 3 分钟
  · 发布 ≤ 18 个月（工具/资讯类）；学术/方法论类可放宽到 3 年
  · 标题或简介明确涉及本议题的核心概念

排除：
  · 纯广告 / 带货（简介含购买链接，且内容无评测）
  · 时长 < 60 秒
  · 纯搬运无原创观点（可留作背景，不进阶段 2）
  · 直播回放且无章节
```

**为什么要写死**：REA 明确指出，筛选标准如果中途改动，**筛完你也不知道自己筛了什么**，结论无法复核。

## 五、预算（在阶段 0 就定死）

| 项 | 默认 | 说明 |
|---|---|---|
| 候选上限 | **40 条** | 去重后进入候选表的条数（`max_candidates`） |
| **工具调用上限** | **40 次** | **单位是工具调用次数**（`scan_topic` 算 1 次）。见 `exit-rules.md` §三 |
| 关键词组上限 | **8 组** | 每组 `per_query=30` |
| 深挖条数上限 | **6 条** | 阶段 2 |
| 补 ASR 条数上限 | **2 条** | 仅无字幕且通过 §三·二 判据的 |
| 时间上限 | 视用户耐心 | 超过要主动汇报进度 |

**预算用尽 → 直接进入阶段 3，不等"再搜一条"。**

> 🔴 **两个单位不能混用（2026-10-22 实测踩坑）**
>
> | 单位 | 谁在报 | 量级 |
> |---|---|---|
> | **工具调用次数** | 预算表、`exit-rules.md` §三 | 一轮 15–45 次 |
> | **上游请求数** | 工具返回的 `cost.calls`、账本里的 `calls` | 一轮 70–350 次 |
>
> 一次 `scan_topic(keywords=[12 个词])` = **1 次工具调用 = 24 次上游请求**。
> 拿 `cost.calls`（323）去跟"工具调用上限"（当时写 30）比，会得出"超支 10 倍"的假结论——
> 2026-10-22 那份报告就是这么写错的。**预算一律按工具调用次数计**；
> 上游请求数只用于算成本（报告 §五「单轮开销」）。
>
> ⚠️ **不要写「上游调用上限 N 次」**：这个口径一开局就注定超支
> （12 个词 = 24 次上游，光扫一遍就吃掉预算），协议里出现时 `write_protocol`
> 会自动在文件里加一行废弃提醒。

## 六、先查已有资产（资产积累型的关键动作）

**本 skill 是长期运行的**。开始新一轮前，必须先：

```
1. registry_get(kind="stats")     → 库里有多少信源 / 视频 / 议题档案 / 协议
2. registry_get(kind="insights")   → 经验库里有哪些可迁移的判断（**全量读**，别只读本议题）
3. registry_get(kind="topics")    → 有哪些议题档案？其中哪些的 gaps / next_entry 与你有关？
4. registry_get(kind="videos", topic="<相关议题>") → 哪些视频已经分析过？
5. registry_get(kind="sources")   → 这个领域有没有已评级的 UP 主？
6. registry_get(kind="protocols") → 有没有已落盘的检索协议（同一议题的第二轮要复用它）
```

**每一步对应"上一轮留下什么"**：

| 查什么 | 得到什么 | 怎么用 |
|---|---|---|
| `stats` | 库的整体形状 | 判断这是新领域还是老领域 |
| `insights` | 跨议题的领域/信源/方法认知 | **开工前先读**——它会告诉你"这类词族会带什么噪声" |
| `topics` | 议题档案：`core_questions` / `covered` / `gaps` / `open_conflicts` / `user_adopted` / `next_entry` | **第二轮的直接起点**：`gaps` 就是这轮该补的，`next_entry` 是上轮定的切入点 |
| `videos(topic=)` | 已分析视频 + `key_findings` + `selected_because` | **已分析过的不要重复深挖**；但要记住它们的存在（结论要能对上） |
| `sources` | UP 主评级 + `grade_basis` | 沿用评级，并标注「沿用历史评级，本次未复核」 |
| `protocols` | 上轮的检索协议 | **同一议题的第二轮必须先读它**——知道上轮搜过什么，才知道这轮该往哪扩 |

> 💡 **第 6 条是"第二轮"的起点**。同一议题跑第二轮时：
> 先 `registry_get(kind="protocol", topic=...)` 读上轮的协议与漏斗数字，
> 然后**扩**（更多词族、更多分P、更长时间跨度、更深的评论），
> 而不是**重来**——更不是照抄上轮的简报。

**这一步能省掉大量重复工作**，也是"资产积累"和"用完即弃"的真正区别。

路径与数据结构见 `references/registry.md`。
